SHARED HTTP API — T2 IMPLEMENTS, T1 CONSUMES
- POST /api/cases: multipart/form-data; summary:string and optional repeated files fields. At least summary or one file is required. Optional text fields: customerName, customerEmail, merchantName, supportPhone, amountMinor, currency. Returns 201 {case:CaseV1}.
- GET /api/cases/:id: returns 200 {case:CaseV1}.
- PATCH /api/cases/:id: JSON {expectedRevision:number, changes:CaseChanges}; returns 200 {case:CaseV1}.
- POST /api/cases/:id/authorize: JSON {expectedRevision:number}; returns 200 {case:CaseV1}, including authorization.id.
- POST /api/cases/:id/calls: JSON {authorizationId:string, requestId:string}; returns 202 {call:CallV1}. requestId is a client-generated UUID, reused for retries of the same action.
- GET /api/cases/:id/packet: returns text/plain; charset=utf-8 as a downloadable refund request with evidence index. PDF is optional after the working flow.
- POST /api/webhooks/dial: accepts raw provider bytes and headers, verifies through the voice adapter, durably deduplicates the event, and processes authenticated call details. Returns 204 only after durably accepting a valid event; invalid signatures return 401.
- Failures use ApiError. Use 400 malformed input, 404 unknown case, 409 revision/authorization/conflicting action, 422 missing required facts, 503 missing live configuration/provider unavailable before dispatch. Do not report an ambiguous dispatch as a safe-to-retry 503; persist dispatch_unknown.

AUTHORIZATION AND STATE RULES
revision starts at 1 and increments only for changes to case facts; timeline/call updates do not increment it. Material edits clear authorization and rebuild the draft. Reject edits while a call is active or dispatch_unknown; preserve the approved snapshot and evidence.
Authorization requires a known customer name, merchant name, E.164 support number, positive integer amountMinor, currency and nonempty reason. /authorize is idempotent for an unchanged revision: reuse its authorization ID, never mint a fresh ID to bypass dispatch deduplication. Reject new authorization while a call is active or dispatch_unknown.
Authorization freezes the exact case revision, contact destination, amount, factual call brief and permitted actions. Never trust replacement facts supplied to the calls endpoint.
MVP permits one dispatch attempt per authorization ID. Atomically persist an attempt before calling Dial. Repeated requestId or authorizationId returns the stored attempt; concurrent requests cannot create two calls.
Once a network request may have reached Dial, timeout/connection loss is dispatch_unknown. Do not automatically redial. Reconcile with provider evidence before a new attempt. If no provider call ID was returned, require a documented correlation/search mechanism or manual verification; never guess a matching call.
Publish a terminal CallV1 state and its processed case outcome/timeline atomically so the UI cannot stop polling before the result appears. If analysis fails, publish an explicit unknown outcome with a next action rather than inventing success.
Maintain call lifecycle separately from refund decisions. A completed call does not imply a refund was approved or paid. An explicit support statement may support "approved" with a quote/reference, while paymentStatus remains unverified without separate payment evidence.
API keys remain server-side. Enforce case ownership using a session-bound cookie or equivalent local-demo access control. Do not expose customer cases through unauthenticated public routes.
Simulated mode must be explicit in data and UI. Never silently fall back to simulation when live operations fail. No real calls during tests; a live test requires a deliberately configured, consenting test recipient.
