CONVERSATIONAL WORKFLOW HANDOFF

Purpose

The three starter prompts begin real, owner-scoped case preparation. They are
not canned scenarios or an alternate fixture runtime. Preparation is distinct
from provider submission, claim acceptance, a completed call, or payment.

Expected user journeys

Amazon shoes refund:
- Ask what happened, the order/date/item, amount if known, and desired resolution.
- Invite the order confirmation, receipt, photographs, or prior support exchange.
- Keep missing facts unknown; an unavailable support number must not prevent
  preparation of a browser action or a case brief.
- Prepare a factual brief, evidence index, and next actions. The browser action
  starts at the reviewed merchant URL; sign-in and material external actions
  remain subject to the browser execution controls.
- Do not call automatically or promise that the return/refund is eligible.

Duplicate subscription charge:
- Ask which subscription, the two charge dates/amounts, whether both settled,
  account identity, and the requested resolution.
- Compare the user's explanation with attached billing evidence. Conflicting
  amounts or dates require clarification rather than silently choosing one.
- Prepare a request for the duplicate amount, with the existing paid charge
  distinguished from the disputed charge. Never infer that every refund request
  concerns a duplicate charge.
- A support call is a separate reviewed action; preparing a plan is not consent
  to dial and the presence of a call plan does not establish a refund outcome.

Car insurance claim:
- Ask the provider/policy, claimant's role, incident date/location, vehicle,
  incident description, other-party details if applicable, and desired next step.
- Invite policy documents, photos, estimate, and report/correspondence as relevant.
- Keep general knowledge-base contacts visibly sourced and subject to recipient
  and plan applicability review. A general claims number is not customer consent.
- Produce a preparation brief and evidence list even when loss value is unknown.
- Prepare distinct insurer/other-party contact actions if supplied and relevant.
  Do not infer fault, coverage, an accepted claim, or a recoverable amount.
- The current refund-oriented VoiceAdapter must not be represented as a completed
  general insurance adjudication or automatic multi-recipient calling system.

Acceptance boundary

Follow-up messages and uploads must survive reload in the same owned case.
Attached evidence must be saved as actual private file bytes and indexed in the
case, with the preparation revision tracking the canonical CaseV1 revision.
Stale edits and another session's case must be rejected. Retrying the same
request must not add duplicate messages, evidence, or revisions. Failed model
requests must not silently become heuristic or successful canned responses.
Preparation must leave external outcome/payment unknown until evidence exists.

API handoff

Canonical case shapes remain in src/contracts/case.ts. The additive workflow
shape is src/contracts/workflow.ts. A workflow references caseId/caseRevision;
it is not another case database or an independently approved copy of the facts.

GET /api/cases/:id/workflow loads the owned workflow and current case.
POST /api/cases/:id/workflow accepts requestId and expectedRevision to analyze
the already saved conversation and evidence without adding another user turn.
The UI starts this analysis when a newly opened workflow is not_started.
POST /api/cases/:id/messages accepts requestId, expectedRevision, and message.
POST /api/cases/:id/evidence accepts multipart requestId, expectedRevision,
optional message, and repeated files. GET /api/cases/:id/workflow/brief downloads
the preparation text. Mutation retries must retain the same requestId and body;
requestId reuse with changed content must fail rather than silently replay.

User messages/evidence are persisted before model work and invalidate stale call
authorization. A failed model request keeps the user's work for review, does not
fabricate answers, and does not advance an external action. The successful model
result is applied only if the canonical case has not changed in the meantime.

An ambiguous response keeps the exact pending request ID, body and File objects
in the current UI session. Retry previous update recovers its saved result; it
does not manufacture another conversation turn or upload. A known failed model
operation is returned as saved failed state on the same-ID replay. Analyze saved
information again starts an explicit new analysis request. A WORKFLOW_BUSY or
WORKFLOW_REVISION_CONFLICT response retains the original request identity.
Preflight REVISION_CONFLICT reloads the current facts without replaying the edit.

The workflow action list populates BrowserPanel with the prepared task, exact
provider URL and host list. Opening that panel does not dispatch a browser action.
BrowserService loads the persisted workflow brief at the canonical case revision,
checks the revision again after loading, and saves that brief as request.txt for
the browser planner and reviewed uploads. Later case edits invalidate the browser
run's action approvals. The browser remains a locally hosted Chromium workflow:
sign-in happens in its actual window, and each external action requires review.
An explicitly rejected first browser start (such as a stale case revision or an
unfinished workflow) releases its saved request so the person can review and edit
the task. Network/5xx failures, unresolved/busy responses and any later rejection
after an ambiguous attempt retain the original request ID and instructions.

Insurance call plans are visible as separate recipient/purpose briefs. They do
not call the legacy refund authorization route. Unknown or unprepared workflows
also cannot expose that approval. Existing refund calls remain separately
reviewed; no workflow plan can create a call outcome or verified payment.

Remaining integration limits

- Initial POST /api/cases does not accept a stable creation request ID. A lost
  creation response can leave an orphaned saved case, and a retry may create a
  second case. Follow-up messages, evidence and analyses have idempotent IDs.
- Request IDs/File references for an ambiguous workflow update are retained only
  while the current UI session remains mounted. Reload reads persisted server
  state and never automatically replays an uncertain mutation.
- Browser execution has reviewed hosts, bounded sessions and explicit action
  approvals. It does not yet establish unattended success on arbitrary provider
  sites, remote browser sign-in, claim eligibility or confirmed money movement.
- General insurance and other-party calls are prepared plans only. They require
  a purpose-specific execution/authorization integration before production use.
