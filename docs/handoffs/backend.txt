FINDINGS FROM T3 (docs/handoffs/dial.txt 12be4ab, Alike ask 8d31fd06) — RESOLVED
1. Mode isolation: authorize and POST …/calls answer 409 MODE_MISMATCH when case.mode !== REFUND_MODE. The check runs
   inside the attempt transaction before any provider side effect; reconciliation and webhook processing never look a
   call up through the other mode's provider. tests/backend/boundary.test.ts.
2. Webhook body bound: POST /api/webhooks/dial streams the body and cancels the stream at 1 MiB, with or without
   Content-Length, answering 413 PAYLOAD_TOO_LARGE before verification. tests/backend/routes.test.ts.
3. Validated config reaches the adapter: the composition root calls
   createDialAdapter({mode:"live"}, {config:{apiKey, fromNumber, webhookSecret?, maxCallDurationSeconds}}) with the
   values from loadConfig(); the adapter never reads process.env on its own. DIAL_MAX_CALL_DURATION_SECONDS is
   validated 60..3600 (absent/blank → 300; invalid → 503 naming the variable, nothing persisted). Adapter rejections
   with MISSING_CONFIG / INVALID_CONFIG / SERVER_ONLY / INVALID_MODE are 503 LIVE_CONFIGURATION_MISSING and release
   the attempt (a server misconfiguration must not consume the user's authorization). Verified with a fake transport
   in a scrubbed environment: Bearer header, Idempotency-Key = attempt id, to, fromNumber, maxCallDurationSeconds=300.
   tests/backend/boundary.test.ts.
4. .env.example duration line commented out (cbb03ed).
5. Late transcript, agreed operational handoff: after the wait window publishes an unknown outcome, each
   GET /api/cases/:id re-reads the provider read-only (at most every LATE_TRANSCRIPT_INTERVAL_MS, default 30 s, for
   LATE_TRANSCRIPT_WINDOW_MS, default 24 h). A transcript that arrives is attached, the outcome is evaluated once,
   and the call stays completed (no regression). There is still no background worker: if nobody opens the case,
   nothing advances until the next GET. Nothing ever redials. tests/backend/transcript-wait.test.ts.
Also: E.164 validation now matches the adapter's rule (+ then 8–15 digits), so a dispatch never fails on format.

ADDITIVE ROUTES (not in V1; safe to ignore)
- GET /api/capabilities -> { liveCall: false, stepIn: false, decisions: false }. No session. The frontend's V2 probe
  (frontend.txt "V2 PROPOSAL"); explicit false is the honest V1 answer, so the call screen degrades to V1 state.
- GET /api/cases/:id/history -> { history: HistoryCheck | null, current: boolean }. Session-bound like GET /api/cases/:id
  (404 for an unknown or foreign case). The stored pre-authorization transaction-history check (Keewano or fixture;
  revision, checkedAt, source, status, summary, matches[], closestGapMinutes); current=false once the facts moved past
  it (GET /api/cases/:id re-checks on read). Does not run a check itself.
- GET /api/insights/merchant?name=<merchant> -> { available: true, merchant, source, cases, approved, denied,
  needsInformation, unresolved, approvalRate (approved/(approved+denied), null when nothing decided), lastOutcomeAt }
  from the cases mirrored into Keewano (one query, last outcome per case, merchant matched like the history check so
  descriptors count), or { available: false, merchant, error? } when no source exists or the query failed/timed out
  (KEEWANO_TIMEOUT_MS). Always 200 once the name is valid; 400 BAD_REQUEST when name is missing, blank or > 200 chars.
  Aggregate reference data, no customer data, so no session cookie. Fixture-backed in simulated mode without a token
  (same switch as the history check). Port: src/server/cases/insights.ts; Keewano/fixture: src/integrations/keewano/insights.ts.
  Tests: tests/backend/insights.test.ts.

KNOWN LIMITS / PROPOSED CONTRACT NOTES (not applied; coordinate before changing V1)
- One attempt per authorization is enforced literally: a definitive pre-dispatch refusal (e.g. provider rate limit)
  consumes the authorization; the user must edit a fact and re-authorize. Proposed V1.1: allow a new attempt when

  is required before any new attempt (nextAction says so). No automatic redial exists anywhere.
- Transcript reconciliation is driven by GET polling (bounded), not a worker; if nobody polls, it resumes on the next GET.
- Simulated mode is explicit in data (mode) and must be labeled in the UI.
