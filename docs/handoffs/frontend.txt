WHAT IT IS
A chat-first assistant. The user uploads insurance plans once, types a request in plain
language, approves the call in one confirmation step, then watches a phone-call screen:
who is being called, elapsed and hold time, whether the agent is talking to a person or
an automated agent, a step-in control, and approval prompts that arrive during the call.
The outcome card shows decision, reference, next action and quote, with approval and
payment as separate rows. No tool registry, mandate card or handshake receipt on screen.

RefundApp is "use client" and self-contained: CSS modules only, tokens on its own wrapper,
no global CSS edits, no new dependencies. It reads only `serverMode`.

API MODE
Default is the real backend over same-origin fetch with credentials: "same-origin".
Fixture mode is explicit: open /?api=fixture. It is labelled "Fixture" in the header and
every case and call it produces has mode "simulated". A failed network request never
substitutes fixture data; it shows an error with a retry.
Fixture scenarios: insurance_claim (default), duplicate_charge ($49.99), needs_evidence,
uncertain_dispatch, call_complete_unconfirmed. Pick one in the header or let the chat
infer it from the message ("claim", "duplicate", "no receipt", "uncertain", "confirm").

CONTRACT V1 USAGE
POST /api/cases multipart (summary, files, optional text fields) -> facts card.
PATCH /api/cases/:id {expectedRevision, changes} on every edit; 409 REVISION_CONFLICT
shows a banner and reloads, never overwrites.
POST /api/cases/:id/authorize {expectedRevision}, then POST /api/cases/:id/calls
{authorizationId, requestId}; requestId is a UUID kept in sessionStorage per
case+authorization so a retry reuses it; the button is disabled while in flight.
GET /api/cases/:id polled every 2.5 s only while status is calling or a call is active
or dispatch_unknown; stops on terminal state and unmount. Server state wins.
GET /api/cases/:id/packet downloaded as a blob.
Errors by code: 400, 401/403 unauthorized, 404, 409 (revision, authorization, call in
progress), 422 lists fields, 503 live configuration missing, network unreachable.
dispatch_unknown renders an explicit warning and never offers a redial.

V2 PROPOSAL (additive, feature detected; nothing in V1 changes)
The call screen needs data V1 does not carry. The http client probes GET /api/capabilities
once; absent (404) means all false and the UI degrades to V1 state plus transcript.
  GET  /api/capabilities -> { liveCall, stepIn, decisions }
  GET  /api/cases/:id/calls/:callId/live -> LiveCallV2
  POST /api/cases/:id/calls/:callId/join -> LiveCallV2 (userJoined true)
  POST /api/cases/:id/calls/:callId/decisions/:decisionId  body { optionId } -> LiveCallV2
LiveCallV2: callId, caseId, calling{name,phone}, phase (dialing | ringing |
navigating_menu | on_hold | talking | waiting_for_user | user_joined | ended),
counterpart (human | agent | unknown), counterpartConfidence 0..1, startedAt, endedAt,
holdSeconds, notes[{at,text}], pendingDecision {id, question, defaultOptionId,
options[{id,label,tone}], expiresAt} | null, userJoined, updatedAt.
Exact TypeScript: src/features/refund-ui/api/types.ts. Suggested source on the backend:
Context MCP tools the voice agent calls mid-call (set_counterpart, report_progress,
request_user_decision), see docs/SPEC.md section 6 and T3's context-mcp-design.txt.

METRICS
Active user time is measured in the browser: seconds the document is focused with a
pointer or key event in the last 10 s. Agent phone time is the live call timer. They are
shown side by side; no savings figure is computed anywhere.
